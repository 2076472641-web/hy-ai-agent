## 一、项目背景介绍

该项目属于典型的 NLP 文本多分类任务，面向小程序电商商家商品上架场景，覆盖服装鞋帽、数码家电、美妆护肤等 **12 个一级类目**，目的是对平台海量商品标题、详情文本自动划分类目，实现商品智能归类，提升商品流转效率。

传统平台全部依靠运营人工手动划分商品类目，不仅人力成本高、不同运营分类标准不统一，还存在商品错分、上新审核大量积压的问题；**大促期间上新量激增 5-8 倍**，人工审核完全积压，**商品上架延迟平均超 48 小时**，商品流转效率极低。

因此本项目通过 AI 智能分类方案，在**模型精度、推理速度和部署成本**之间做好平衡，解决平台商品人工分类低效、类目划分精准度不足的核心痛点。

## 二、工作职责介绍

本项目由我从 0 到 1 独立搭建并落地，完整覆盖 NLP 项目工程全流程。主要工作包括五点：

### 2.1 数据预处理
我做了 **12 步完整清洗流水线**：HTML 实体解码 → 剥离 HTML 标签（含 script/style 块）→ 去 URL/邮箱 → 去除 emoji 表情 → 繁简转换 → 全角半角转换 → 特殊字符过滤 → 连续重复标点压缩 → 空白字符归一化 → 最小长度校验 → **jieba_fast 高速分词** → **电商 200+ 定制停用词过滤**；

同时做去重、去空值，**8:1:1 分层抽样**划分训练验证测试集，并跑完整 EDA 分析输出 6 类图表（类目分布柱+饼图、标题详情长度直方+箱线图、高频词柱图、全局+分类目词云、相关性热力图）。

### 2.2 特征工程体系搭建
我设计了**双路径 FeaturePool 特征池**：
- **无监督路径**：构建词级 TF-IDF（5000 维 1-2gram）、字符级 TF-IDF（2-4gram）、BERT 嵌入（CLS/Mean-Max 双池化）、Ngram 词频共 4 大类特征组；
- **有监督路径**：用卡方、互信息、树模型重要性做 Top-K 筛选；
- **冗余剔除**：先低方差过滤、再 >0.95 高相关贪心剔除；
- 最后用 **LGBM + 3 折 CV 暴力枚举特征组合**，自动找到 F1 最高的配方。

### 2.3 多模型训练搭建
我采用**分层递进对比**的思路，先后构建 4 类模型：
- 随机森林（TF-IDF 拼接特征，200 棵树、max_depth=30、**class_weight=balanced**）
- FastText（wordNgrams=2、dim=128、bucket=20 万）作为基线
- bert-base-chinese 微调（max_length=128，LR=2e-5，**warmup=0.1，权重衰减 0.01，梯度累积 2 步，FP16 混合精度**）
- 通用大模型 Prompt 工程（5 套模板含 CoT）的对比实验

### 2.4 模型优化迭代
通过 **INT8 三档量化**（动态/静态/QAT）、**DistilBERT 知识蒸馏**（T=4、α=0.5，损失=0.5 KL 散度×T² + 0.5 交叉熵）、**ONNX 动态 batch 导出**三条线完成轻量化，并配套 **Benchmark 基准测试工具**测 P50/P90/P99 延迟+吞吐量+内存占用。

### 2.5 工程化与服务化落地
基于 **Click 框架**实现了 7 个命令的 CLI 工具链：`generate-data / preprocess / train / compress / evaluate / serve / pipeline`，其中 `pipeline` 命令一键跑通全流程；

**FastAPI** 搭了单条分类、批量分类、模型管理、运营纠错反馈 4 类接口；
**Streamlit** 实现运营可视化后台；
**ModelManager** 支持多模型热加载和版本切换；
**纠错反馈闭环**直接把错分样本写入 feedback.csv，支持后续增量训练。

## 三、技术选型部分

我采用**分层对比、逐级迭代**的选型思路：

### 第一层：随机森林 + FastText 做基线
优点是训练快（RF 训完 2 分钟、FastText 30 秒）、部署轻（RF+TF-IDF 一共几十 MB、FastText 单 bin 文件几 MB）、可解释性强（TF-IDF 能看词权重）；缺点是语义理解弱，**FastText F1 ≈ 0.84，RF F1 ≈ 0.88**。

### 第二层：BERT 微调做主力模型
`bert-base-chinese` 经过 3 轮微调后 **F1 冲到 0.957**，比 RF 高约 8 个百分点，语义理解能力强，对同义词、隐含品类词（如"老爹鞋"归鞋类）识别准确；代价是模型大（420 MB）、推理慢（CPU 单条 120 ms）。

### 第三层：通用大模型零样本分类（最终未采用）
我也试了直接调用通用大模型零样本分类，但最终没用，原因有三：
1. 通用模型没有电商领域微调，细粒度术语经常错；
2. 上下文窗口塞不下 12 类完整定义+示例，零样本效果不稳定；
3. **推理成本是 BERT 的 60-80 倍、延迟慢 10-20 倍**，高并发场景完全不可行。

所以 LLM 只保留作为后续做 Agent 规则迭代的方向。

### 评估指标
评估上我不是只看一个 F1，而是 **6 维综合**：Accuracy、Precision-Macro、Recall-Macro、F1-Micro、F1-Macro 加完整分类报告；其中以 **F1-Macro 为核心指标**，因为它给每个类目相同权重，对小类目更公平。

## 四、问题解决部分

项目开发过程中我也遇到过三个典型问题。

### 4.1 商品文本长短差异大导致的信息丢失
商品标题 10-30 字，详情 300-2000 字，默认 512 截断会丢规格参数，只取尾部又错过标题品牌品类词。我做了**四层策略**：
1. **字段加权合并**：`title + [SEP] + 详情前60% + [SEP] + 详情后40%`，组合成 combined_text 保证标题 100% 保留；
2. **长度自适应裁剪**：超长时优先牺牲详情中间段的滑动窗口裁剪；
3. **BERT max_length 从 512 降到 128**——实验发现电商任务 128 已经覆盖 96% 有效信息，注意力更集中，**F1 反而高 0.3 个点，速度快 3.2 倍**；
4. 配合 jieba_fast 分词 + 200+ 电商停用词表减少无效 token。

这套策略上线后，**长尾规格类商品（如"XXL 码藏青色纯棉加厚卫衣"）的识别错误率从 11.2% 降到 3.8%**。

### 4.2 样本不均衡，冷门商品常被分到热门大类
宠物用品、珠宝饰品这类小类目样本只有服装的 1/3，初期小类目召回率只有 63%。我打了**三层组合拳**：
1. **数据层**：stratify 分层抽样保证每折类目分布一致；
2. **算法层**：RF 开 `class_weight=balanced`，BERT loss 乘类目样本数倒数，加大小类错分惩罚；
3. **评估层**：改用 F1-Macro 做核心指标，逼模型不能靠"押大类"刷分。

组合拳后，**12 个类目的 F1 标准差从 0.18 降到 0.06**，最差的宠物用品类 F1 从 63.2% 拉到 89.7%，整体 Macro-F1 提升 4.6 个百分点。

### 4.3 原生 BERT 体积大、推理慢，线上扛不住并发
原生 bert-base-chinese CPU 推理 120-150ms，420MB，单机每秒约 7 条，大促 1000QPS 需要 6 台机器。我给出了**轻量化三档方案**：

#### 一档：INT8 动态量化
只量化 Linear + Embedding 权重，无需校准数据，**体积 420MB → 110MB（压缩 3.8x），延迟 120ms → 48ms（加速 2.5x），F1 只降 0.006**，几乎感知不到。

#### 二档：DistilBERT 知识蒸馏
教师 12 层 BERT → 学生 6 层 DistilBERT，蒸馏温度 T=4、alpha=0.5，**损失 = 0.5×KL(T)×T² + 0.5×CE**，3 轮早停后：
- 参数量 108M → 66M（压缩 1.6x）
- 体积 420 → 240MB（压缩 1.8x）
- 延迟 120 → 46ms（加速 2.6x）
- **F1 从 0.957 → 0.949，几乎无损**。

#### 三档：ONNX 导出 + 动态 batch
支持 batch=1-64 自适应，单条延迟进一步降到 38ms，**batch=64 时吞吐量 320 条/s vs 原生 PyTorch 的 85 条/s**。

#### 线上最终部署
「蒸馏版 + ONNX」组合拳：**体积↓43%，单条延迟↓68%（120ms → 38ms），吞吐量↑3.8 倍**，F1 只降千分之八；大促 1000QPS 2 台 4核8G 机器搞定，省了 2/3 服务器。

## 五、项目收获

通过本次项目，我有三个核心收获：

### 收获一：完整掌握 NLP 项目从 0 到 1 的全链路闭环能力
不只是训过模型，而是独立走完「需求定义 → 12 类目体系设计 → 模拟数据生成 → 12 步文本清洗 → 分词 → 特征池构建 → 4 模型分层训练 → 3 档轻量化压缩 → 6 维评估 + Benchmark → FastAPI 接口 + 纠错闭环 → Streamlit 后台 → CLI 工具链 → 一键 pipeline」的完整路径，**每一步既知道怎么做，也知道为什么选这个方案而不是另一个**。

### 收获二：积累了 BERT 微调与线上性能调优的实战经验
从"只知道 BERT 能训"到搞懂——warmup 策略为什么设 0.1、梯度累积怎么等价扩 batch、蒸馏 T 为什么取 4 而不是 2、量化对哪些层最有效、DistilBERT 相比原生 BERT 到底丢了哪层信息；也学会了用 **P50/P90/P99 延迟、吞吐量、内存占用**这些工程指标而不是只看 F1 来评估模型。

### 收获三：养成了「量化驱动 + 可复现 + 可协作」的工程思维
虽然这个项目是我独立开发的，但我刻意按团队协作标准去做：
1. 所有超参数集中在 `config.yaml`，不写魔法数字；
2. `seed_everything(42)` 统一 numpy/torch/random 种子，保证别人跑我的代码能复现同样的 F1；
3. 所有模型统一继承 `BaseClassifier` 抽象基类，新同学加个 TextCNN 模型只要实现 6 个方法就能无缝接入训练、评估、压缩、部署全流程；
4. 所有实验结果存成 CSV 报告，不存口头记录。

这种「**假设 → 实验 → 量化 → 迭代**」的严谨思维，比单独掌握一个算法有价值得多。
