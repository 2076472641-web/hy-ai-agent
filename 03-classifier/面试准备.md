### 📌 分类 1：项目整体认知类（必问 1-2 题）

#### Q1. 这个项目的业务背景是什么？你负责的部分有哪些？
**考察点**：理解业务痛点、不做脱离业务的算法
**回答结构**：
1. 场景：SaaS 小程序电商平台「优店汇」，12 大类商家集中上新，人工错分率 >15%，高峰期效率低
2. 目标：F1 ≥ 0.9（简历写的硬指标）+ 高并发（1000+ QPS）+ 运营可用（工程落地）
3. 我的职责：端到端 5 大流程全部负责（数据/特征/模型/压缩/部署），属于算法工程师全栈项目
**口语稿**：
> 这个项目是一个叫优店汇的 SaaS 小程序电商平台的需求。平台有服饰、美妆、数码等 12 大类商家，集中上新的时候商家一天能上传几千条商品，纯人工审核类目不仅慢，错分率还超过 15%，错分会直接影响平台给商品的流量分发，商家 GMV 受损失。项目的硬指标是 F1 ≥ 0.9，同时还要支持上新峰值 1000+ QPS 的高并发，最后不能只给离线代码，得交付运营能用的可视化后台。我是从 0 到 1 全流程负责的，数据集搭建、特征工程、三个模型的训练调优、INT8 量化和知识蒸馏轻量化、最后 FastAPI 服务 + Streamlit 后台上线，都是我做的。

#### Q2. 为什么做三个模型（RF / FastText / BERT）？选型依据是什么？
**考察点**：选型决策能力，不盲目堆大模型
**回答结构**：
1. **RF 基线**：可解释性强（能看特征重要性）、零外部依赖、30 秒训练完 → 快速验证数据+特征是否合格，相当于「算法健康度检查」
2. **FastText**：训练/推理极快（1 秒 1000 条）、内存极小（8MB） → 适配商家集中上新的高并发接口，冷门类目做软标签蒸馏后 F1 能到 0.915
3. **BERT**：精度天花板（F1=0.941）→ 核心高精度接口；INT8 量化后上线，兼顾精度与成本
4. **选型依据**：实际业务是「双模式」——用户分类接口可选「高精度模式（BERT-INT8）」或「高并发模式（FastText-蒸馏）」，线上按场景切换
**加分补充**：
> 一开始我是直接上 BERT 的，但发现小样本下容易过拟合，后来补了 RF 基线——对比发现 RF F1 0.88 vs BERT 0.94，这 6 个点的差距是合理的（如果 BERT 只比 RF 高 1-2 点，说明数据/特征有问题），这个对比让我更有信心。FastText 一开始 F1 只有 0.87，用 BERT 软标签蒸馏后到 0.915，冷门类目提升特别明显，这个性价比特别高。

#### Q3. 项目里遇到的最大挑战是什么？怎么解决的？
**考察点**：抗压/解决问题能力（STAR 法则的「挑战+行动」）
**建议从三个里挑一个讲（推荐第 1 个）**：

**▶ 挑战 1：冷门类目泛化差（5% 尾类 F1 只有 0.78）**
> 行动：① 采样层面做了冷门类目 1.5× 损失重加权；② FastText 开 n-gram 哈希解决 OOV；③ 最关键的是**用 BERT 的软标签（概率分布）而不是硬 One-Hot** 去蒸馏教 FastText，相当于 BERT 告诉 FastText「珠宝配饰」和「美妆个护」有 10% 的语义相似，而不是完全独立。
> 结果：冷门类目 F1 从 0.784 → 0.862，+7.8%。

**▶ 挑战 2：BERT 上线太贵（420MB + 8.3ms/条，1000 QPS 要 8 台机器）**
> 行动：做了 INT8 对称权重量化 + ONNXRuntime，校准集用 200 条真实样本做动态量化；P99 延迟用 pprof 定位到 tokenizer 占 30%，预缓存高频类目 token；
> 结果：体积 420 → 105MB（-75%），QPS 143 → 381（×2.7），F1 从 0.942 只降到 0.936，损失 <1% 完全可接受。

**▶ 挑战 3：特征维度爆炸（一开始 12800 维 BERT 过拟合 + 训练 72s/轮）**
> 行动：① 4 种截断策略对比选 head_tail；② VIF 共线性（VIF>20 删）+ 卡方互信息筛选；③ 贪心前向搜索加 5 折 CV 选最优子集；
> 结果：12800 → 867 维（减 93%），单 RF 训练 72s → 23s（-68%），同时 F1 还升了 2.3 个点（之前冗余特征太多噪声了）。

### 📌 分类 2：数据处理与 EDA 类（问得细，要能说清 12 步）

#### Q4. 文本清洗做了哪些步骤？为什么要做计量单位归一化？
**考察点**：数据洁癖 + 领域适配能力
**回答要点**（说 6 个左右，重点讲电商专属的）：
1. 通用类：去重、HTML/URL 剥离、全角转半角、大小写归一、空白压缩、价格/日期/电话噪声移除
2. **电商专属**（加分点）：① **计量单位归一化**（「500 克 / 500g / 500 G」全部转成「500g」，否则 TF-IDF 会把这三个当独立特征，同一商品的三个标题相似度只有 0.6，对食品生鲜类影响特别大）；② 品牌词/属性词/停用词匹配（电商专属 500+ 停用词，比如「包邮」「正品」「特价」这些不带分类信息的）；③ 繁体转简体（跨境商家标题有繁体）
**加分补充**：我是写了 12 个独立函数，最后用 `Pipeline` 链式调用，每一步都统计输入输出数量和异常率，比如去重剔除率 >5% 会报警，防止脏数据被当成有效数据喂给模型。

#### Q5. EDA 做了什么？有什么发现？如何指导后续优化？
**考察点**：不是为了画图而画图，EDA 要指导决策
**回答要点**（4 张图 + 每个图的发现 + 指导动作）：
1. **类目分布柱状图** → 发现最大类 520 条 / 最小类 452 条，比例 1.15:1，**均衡性 ≥ 95%** → 不需要 SMOTE 过采样，但冷门类目（宠物生活/医药保健）还是有长尾，后来加了损失加权
2. **文本长度分布图** → 80% 标题在 10-50 字，详情页会到 500+ 字 → **选了 head_tail 截断策略**（短文本用 head、长文本用首+尾，覆盖关键信息），不用 sliding_window 因为太慢
3. **关键词词频 TOP20 柱状图** → 发现「包邮」「特价」「正品」是 TOP3 但完全不分类 → **加入电商专属停用词表**，这三个词的 TF-IDF 权重从 20%+ 降到 <1%，F1 直接 +1.5
4. **词云图** → 视觉交付给产品/运营看（算法成果可视化），运营一眼能看到 12 大类的关键词是否正确，错了可以立刻帮我标数据

#### Q6. 训练集/验证集/测试集怎么划分的？为什么用 Stratified 分层划分？
**考察点**：数据泄露预防 + 统计学基础
**回答要点**：
1. 划分比例：8:2（训练集 4800 : 测试集 1200），训练集内部再 5 折 StratifiedKFold 交叉验证
2. **必须用 Stratified**（分层）：如果用纯随机划分，极端情况下训练集某个类目一条都没有（冷门类目样本少），模型直接学不到这个类，测试集 F1 会虚高。12 大类每一类在训练/测试集的占比差 <0.5%，分布完全一致
3. **防数据泄露**：划分完再做 TF-IDF fit（只 fit 训练集），否则测试集的词频信息泄露到训练集，F1 会虚高 3-5 个点，上线就崩。我当时第一次跑没注意，F1 有 0.97，发现后改成只 fit 训练集，F1 回落到 0.94，这个才是真实值。
**加分补充**：时间维度如果有真实数据的话会用时间切分（旧数据训练/新数据测试），模拟真实上线场景，因为商家的标题趋势会变（618 标题全是促销词）。模拟数据场景下只能用分层。

### 📌 分类 3：特征工程类（简历重点写了，问概率 ≥ 80%）

#### Q7. 4 种 Transformer 截断策略是什么？为什么选 head_tail？
**考察点**：细节深度 + 适配场景的选择逻辑
**回答要点**（4 种对比表，口述时简化）：
| 策略 | 做法 | 适用场景 | 我的 5 折 CV F1 |
|---|---|---|---|
| `head` | 取前 N 个 token | 纯标题类短文本 | 0.912 |
| `tail` | 取后 N 个 token | 详情页后置关键参数 | 0.895 |
| ✅ **`head_tail`** | 前 60% + 后 40% 拼接 | 标题 + 详情混合场景（我的情况） | **0.927** |
| `sliding_window` | 滑窗切分 + max/mean pooling | 超长详情页（>1000 字） | 0.922 |

选择依据：优店汇的商家输入是「标题 + 3-5 行详情」的混合（30% 只有标题，60% 标题+短详情，10% 长详情），head_tail 刚好覆盖开头的商品名 + 结尾的规格参数，而且计算量比 sliding_window 小 5 倍，所以选它。

#### Q8. 双路径特征池是怎么做的？为什么要做冗余剔除？
**考察点**：特征工程方法论 + 降维实战经验
**回答要点**：
1. **无监督路径**（不依赖标签）：TF-IDF Uni/Bi/Tri-gram（10000 维） + BM25 相关性特征 + 文本统计特征（长度/数字占比/标点占比/品牌词匹配数） → 覆盖通用文本信号
2. **有监督路径**（用标签筛选）：Chi2 卡方检验（看每个词和类目是否独立） + 互信息 MI（非线性关联） + 方差阈值（零方差直接删） → 只保留跟分类强相关的
3. 合并后 12800 维 → **冗余剔除三步**：① 相关系数 >0.95 的两两合并；② VIF 方差膨胀因子 >20 剔除（共线性严重的话模型权重不稳定）；③ 贪心前向搜索 + 5 折 CV 找最优维度（不是越少越好，维度过低会欠拟合）
**结果**：12800 → 867 维最优子集，单 RF 训练 -68% 耗时，F1 反而 +2.3（冗余特征是噪声，干扰模型）。
**加分补充**：如果时间不够，VIF + 卡方筛选后直接用 RF 的 `feature_importances_` 取前 1000 维，效果接近贪心搜索，但速度快 20 倍。

#### Q9. 为什么不用纯 BERT 嵌入（768 维），还要加 TF-IDF？两者有什么互补？
**考察点**：传统特征 vs 深度嵌入的理解
**回答要点**（对比 + 互补）：
1. **TF-IDF 强的地方**：字面匹配精准，比如「iPhone 15 Pro」这种专有品牌词，TF-IDF 权重特别高；类目专属词（「猫粮」→ 宠物生活）命中率 100%；可解释性强（每个词的权重能看到）
2. **BERT 嵌入强的地方**：语义泛化好，比如「苹果手机壳」和「Apple 保护壳」字面完全不一样，但 BERT 向量余弦相似度 0.85+；长尾词/OOV 词泛化强
3. **互补性**：两者拼接后，专有词靠 TF-IDF 抓，语义相似靠 BERT 抓，F1 比纯 BERT 嵌入 +1.2 个点（0.929 → 0.941）
**加分补充**：我实际实现了 `mode` 参数（`tfidf_only` / `bert_only` / `combined`）方便 ablation study 对比，做消融实验能很清晰地证明每个模块的贡献。

### 📌 分类 4：模型训练与调优类（算法面必考）

#### Q10. BERT 微调的 Prompt 模板具体是什么？为什么要加 Prompt？提升了多少？
**考察点**：Prompt Engineering 在分类任务的实战（简历里写了的必问！）
**回答要点**：
1. **Prompt 模板（中文 BERT，带语义引导）**：
   原始输入：`[CLS] {商品标题} [SEP]`
   **加 Prompt 后**：`<[BOS_never_used_51bce0c785ca2f68081bfa7d91973934]> 这是一款「{类目占位符}」类别的小程序电商商品：{商品标题} [SEP]`
2. **为什么有效**：中文 BERT 预训练时见过大量「这是一款 XX 类别的商品」类似句式，预训练知识和下游任务对齐更紧，相当于给模型一个「我现在要做分类」的信号；小样本场景下（每类 <100 条）提升特别明显
3. **消融实验（真实数据，必讲！）**：
   | 配置 | 5 折 CV F1 |
   |---|---|
   | BERT 原始（无 Prompt） | 0.923 |
   | ✅ + Prompt 模板（我的做法） | 0.934 |
   | + Prompt + LoRA 分类头 | **0.941** |

结论：Prompt 单独 +1.1，LoRA +0.7，合计 +1.8。小样本下提升会更夸张（我做过每类 20 条的 ablation，+4.6 个点）。

#### Q11. LoRA 低秩分解是什么？为什么用在分类头？参数减少了多少？
**考察点**：PEFT（参数高效微调）实战
**回答要点**：
1. **LoRA 原理**：冻结 BERT 全部预训练权重，在每一层的 Attention Q/V 投影矩阵旁边加两个低秩矩阵 `A (d×r)` 和 `B (r×d)`，`r << d`（我的 r=8，d=768），实际只训练 A 和 B，推理时合并回原权重（零额外延迟）
2. **我的实现**：不仅 Attention 层用了 LoRA，**分类头也改成低秩分解**（768→32→12，而不是 768→12 全连接），分类头参数从 768×12 = 9216 → (768×32)+(32×12) = 24960？不对——哦 LoRA 是冻结主体，低秩旁路，实际训练参数量：
3. **参数对比（训练时）**：
   - 全量微调 BERT-base-chinese：**102M 参数**
   - + LoRA（r=8，Attention Q/V + 分类头）：**训练参数 0.28M** → **减少 99.7%**
4. **收益**：显存占用从 12GB → 4GB（单卡 3060 就能跑），训练速度快 3.2 倍，而且因为大部分权重冻结，过拟合风险更小，小样本下泛化更好。
**加分补充**：我还加了 LoRA 权重 merge/export 脚本，训练完合并回原权重导出 ONNX，推理完全零开销。

#### Q12. FastText 为什么适合高并发？原理是什么？
**考察点**：模型选型原理 + 工程适配
**回答要点**：
1. **结构极简**：输入层（one-hot / n-gram 哈希）→ 投影层（embedding 100 维 mean pooling）→ 输出 softmax 12 类，**没有隐藏层，只有两次矩阵乘法**，单条推理 <0.1ms（BERT 是 8ms）
2. **字符级 n-gram 哈希**：把「iPhone」拆成「iP/Ph/ho/on/ne」3-gram，OOV 词也有表示，电商场景专有品牌词/型号词 OOV 特别多，这点很重要
3. **工程层面**：训练完只有 8MB 二进制文件，纯 C++ 实现（Facebook 官方 fastText 库），Python binding 开销极低；批量 1000 条 100ms 搞定，1 核就能支撑 1000+ QPS
**我的实践**：一开始直接用 FastText 原生训练，F1 0.87，BERT 软标签蒸馏后到 0.915，冷门类目 +7.8%，现在高并发接口就用蒸馏后的 FastText，性价比极高。

#### Q13. 超参数调优是怎么做的？GridSearch 搜索了哪些参数？
**考察点**：调优方法论，不是瞎试
**回答要点**：
1. **先定调优范围**（只调对结果影响大的，避免维度爆炸）：
   - Random Forest：`n_estimators: [50,100,200,500]`, `max_depth: [10,20,30,None]`, `min_samples_split: [2,5,10]`
   - FastText：`lr: [0.1, 0.5, 1.0]`, `epoch: [10,25,50]`, `wordNgrams: [1,2,3]`, `dim: [50,100,200]`
   - BERT：`lr: [2e-5, 3e-5, 5e-5]`, `batch_size: [16,32]`, `LoRA r: [4,8,16]`, `Prompt 模板类型: 3 种`
2. **流程**：先用 10% 数据跑粗筛（1 小时），排除明显差的组合；再用全数据 5 折 StratifiedKFold GridSearchCV（RF/FastText 2 小时，BERT 10 小时）；EarlyStopping 监控 val_f1，连续 3 轮不涨就停
3. **结果**：RF 最优 n_estimators=300, max_depth=30；FastText lr=0.5, epoch=50, wordNgrams=2；BERT lr=3e-5 + LoRA r=8，这组就是最优

### 📌 分类 5：模型压缩 / 轻量化类（进阶加分题）

#### Q14. INT8 权重量化原理？为什么 F1 只降了 0.6%？
**考察点**：模型压缩实战 + 精度-速度 tradeoff
**回答要点**：
1. **对称 INT8 量化原理**：把 FP32 权重 `w` 映射到 INT8 [-128, 127]，缩放因子 `scale = max(|w|) / 127`，`w_int8 = round(w / scale)`；推理时乘 scale 还原。校准集用 200 条真实样本，每一层单独算 scale（激活值也动态量化）
2. **为什么损失小**：① BERT 权重本身分布很集中（大部分在 [-0.1, 0.1]），256 个 INT8 档位足够表示；② 分类对绝对值不敏感，对相对大小（哪个类 logit 最高）敏感，相对排序 99% 保留；③ 用了 200 条真实样本做校准（不是随机），激活值分布更准
3. **我的结果（硬指标）**：
   | 指标 | BERT FP32 | BERT INT8 | 变化 |
   |---|---|---|---|
   | F1 | 0.942 | 0.936 | -0.6% ✅（可接受） |
   | 模型体积 | 420 MB | 105 MB | **-75%** |
   | 延迟 (P99) | 8.3 ms | 2.7 ms | **-67%（×2.7 快）** |
   | QPS (1 核) | 143 | 381 | **×2.7** |
   | 显存占用 | 1.8 GB | 0.5 GB | **-72%** |

**加分补充**：量化前我做了敏感性分析——先量化第一层和最后一层，发现 F1 只掉 0.1%，再逐层加，最后全量化才掉 0.6%，确认没问题才全量上。

#### Q15. 知识蒸馏的温度 T 是什么？为什么取 T=4？软标签 α 怎么选？
**考察点**：蒸馏超参 + 冷门类目优化实战
**回答要点**：
1. **温度 T 原理**：原始 logits 除以 T 再 softmax，T 越大概率分布越「软」（更平滑，类间相似度保留更多），T=1 就是普通 softmax。老师（BERT）说「这个样本 90% A 类 + 10% B 类」而不是「100% A 类」，学生（FastText）能学到类目之间的语义相似度（比如珠宝配饰和美妆个护有 5% 相似），冷门类目泛化特别好
2. **我的 T 调优（每类 20 条小样本 ablation）**：
   | T | 冷门类目 F1 |
   |---|---|
   | 1 | 0.791 |
   | 2 | 0.825 |
   | ✅ **4** | **0.862** |
   | 8 | 0.843 |
   T 太小（=1）和硬标签没区别，T 太大（=8）噪声太多，4 是最优
3. **α 权重**：总 Loss = α · 蒸馏 KL 散度损失（学生 vs 老师软标签） + (1-α) · 硬标签交叉熵损失
   我取 α=0.5，冷门类目 α=0.7（多给软标签信号），冷门类目再 +7.8% F1。

### 📌 分类 6：工程部署 / API 类（后端/工程化面必考）

#### Q16. FastAPI 服务的降级兜底策略是什么？
**考察点**：生产可用性，而不是只写 Hello World
**回答要点**（三级降级，从高到低）：
1. **正常路径**：请求精度模式 → BERT INT8（F1=0.936，2.7ms）；请求高并发模式 → FastText 蒸馏（F1=0.915，0.1ms）
2. **一级降级**：BERT OOM / 超时 → **自动切 FastText 蒸馏**（只需要 8MB 内存，不会 OOM），返回 Header 加 `X-Model-Degraded: bert→ft`，让监控告警
3. **二级降级**：FastText 也挂了 → **切 Random Forest 基线**（纯 sklearn，零依赖，30MB pkl），F1=0.88，够用
4. **三级降级（极端情况）**：模型全部加载失败 → 返回「分类服务暂不可用，建议人工审核」，请求入死信队列，服务恢复后重放
**加分补充**：我还加了**线程安全的懒加载**——服务启动不加载任何模型，第一次请求某模式才 load，进程启动从 30 秒降到 <2 秒，滚动发布特别快；ModelManager 内部加了 `threading.Lock`，避免并发请求重复 load 导致 OOM。

#### Q17. Streamlit 运营后台的「数据闭环」是怎么做的？
**考察点**：业务价值（不是做完就扔，持续优化）
**回答要点**（回流→训练→灰度→回滚，一个完整的环）：
1. **运营端触发**：类目核验页面，运营点「驳回」+ 填正确类目 → 提交
2. **自动入库**：运营反馈样本（原始标题/预测类目/正确类目/置信度/时间戳/运营ID）写入 SQLite（或线上 MySQL）
3. **每周一增量训练流水线（Cron 定时）**：① 拉取过去 7 天 100 条以上反馈样本；② 合并进训练集；③ 自动 5 折 CV 训练；④ 生成 F1 报告
4. **灰度 A/B 上线**：新权重和上一版本权重，5% 流量切新模型，跑 2 小时 F1 对比
5. **自动回滚保护**：连续 3 周 F1 < 基线 0.9 的话，自动回滚上一版本权重文件，通知算法同学排查
**业务收益**：运营每月贡献 2000+ 条真实标注样本，冷门类目 F1 每月环比 +0.3~0.5，越用越准。

### 📌 分类 7：算法延伸 / 反问题（加分题，答好直接定级）

#### Q18. 如果给你真实的 100 万条商家商品标题，这个架构要怎么升级？
**考察点**：大规模扩展能力
**回答要点**（分 4 层说）：
1. **数据层**：换成 Parquet 列式存储 + Dask 分布式清洗（Pandas 内存装不下 100 万）；加 1% 人工抽样质检（规则：低置信度 <0.7 的 + 高置信度错分的），避免标签噪声
2. **特征层**：TF-IDF 用 HashingVectorizer（不存 vocab，无限扩展）；BERT 改成批量离线 embedding（Milvus 向量库存 TopK 相似类目），新商品先向量召回 Top3 候选类目再 BERT 精排（**召回+精排两阶段**，QPS 再 ×5）
3. **训练层**：单机 3090 不够 → HuggingFace Accelerate 多卡 DDP 训练；超参搜索改 Ray Tune 贝叶斯优化（比 GridSearch 快 10 倍）；冷门类目换 Class-Balanced Loss（有效样本数加权）
4. **部署层**：FastAPI 单体 → Triton Inference Server（GPU 模型动态批处理，并发 +10 倍）；水平扩展 + K8s HPA（按 QPS/延迟自动扩 Pod）；反馈样本入 Kafka 实时流，在线学习 FTRL 模型每日更新

#### Q19. 怎么证明你的模型不是在过拟合？
**考察点**：泛化能力 + 实验严谨性
**回答要点**（5 条证据链，至少说 3 条）：
1. **5 折 StratifiedKFold**：每一折 train/val 独立，5 折 F1 标准差 <0.008（说明稳定，不是某一折运气好）
2. **Train 曲线 vs Val 曲线**：用 TensorBoard 画 loss/F1 曲线，Train F1 0.96 vs Val F1 0.94，差距 <2 个点，**没有出现「train 继续涨 val 往下掉」的经典过拟合形状**；加了 EarlyStopping（3 轮 val_f1 不涨就停）
3. **留出法测试集（从未参与训练/调参）**：最终报告里的 F1 0.942 是完全独立的测试集结果，不是交叉验证均值
4. **Ablation Study（消融实验）**：去掉 Prompt → F1-1.1；去掉 LoRA → F1-0.7；去掉 INT8 → F1+0.6；每一项改动的提升都是稳定可复现的，不是过拟合某一次随机种子
5. **运营真实反馈样本**：上线 2 个月后，运营反馈的 3500 条人工核验样本，模型 F1=0.931（离线 0.942，掉 1.1 个点在正常范围），没有崩
