# 智慧旅行助手 - 项目介绍

## 项目概述

面试官，我做的这个项目叫**智慧旅行助手**，主要解决用户出行规划的痛点。

---

## 业务痛点与目标

### 业务痛点

用户做旅行规划的时候，需要分开手动查天气、车票机票、景点票务，来回切换多个平台，多次检索，操作繁琐，规划效率很低。

### 项目目标

做一套 **端到端一站式出行规划系统**，整合各类出行查询能力，用户只需要提需求，系统直接输出完整旅行方案，提升出行规划的便捷性。

---

## 技术架构

这是一套基于**分布式AI 的多 Agent 协作系统**，核心用到大模型LLM、A2A 协议、MCP 模型上下文协议。

### 核心概念

**第一是 Agent**：Agent 就是「大模型 LLM + 任务规划 + 工具调用 + 记忆模块」，是能够自主思考、规划任务、调用工具、留存历史上下文的智能程序。

**第二，A2A 是 Agent 之间的通信协议**：用来实现多个智能Agent 互相协作，拆分复杂旅行任务。

**第三，MCP 是模型上下文协议**：负责让大模型安全调用外部第三方工具和接口。

---

## 三层架构

整个系统整体分为三层架构：**Agent 层、MCP 层、数据层**。

### 1. Agent 层（整个系统的大脑）

接收用户的旅行需求，做任务拆解、规划，判断需要调用哪些外部工具，同时维护对话记忆。

> 比如用户要规划去某地旅行，Agent 会自动拆解任务：先查目的地天气，再查交通票务，再查询景点服务。

### 2. MCP 层（中间连接层）

承接Agent 下发的指令，对接外部系统，执行工具调用逻辑，把查询到的原始结果回传给上层 Agent。

### 3. 数据层（底层数据源）

封装各类查询服务，提供天气、票务、旅行服务等真实数据查询能力。

---

## 完整业务链路

用户输入旅行需求，Agent 层完成任务拆解；通过 MCP 协议调用底层工具，去数据层获取天气、票务、景点等原始数据；多个 Agent 依靠 A2A 协议互相协同处理多份查询结果；最后由 LLM 理解、整合全部信息，直接输出一份完整可直接使用的旅行规划给到用户。

---

## 项目价值

把原本需要用户手动多次检索的工作交给多智能体自动完成，实现一站式旅行规划，降低用户规划的操作成本。

---

## 完整链路流程

用户向Client Agent提交任务，任务经Server Agent、MCP客户端、MCP服务端下发至Tool执行，执行结果再沿原链路逐层回传，最终由Client Agent向用户输出结果。

---

## 常见面试问题

### 一、项目里面一共有4个 Agent，全部在 Agent 层

#### 路由Agent（主 Agent）

整个系统的入口总调度Agent

- **内部模块**：LLM + Planning+React 规划推理模块 + AgentNetwork 智能体网络
- **职责**：接收用户原始 query，做任务理解、任务规划；管理 AgentNetwork，发现、调度底下各个子 Agent，分发子任务。

#### 天气Agent（A2AServer）

专门负责天气相关任务；内部自带LLM、MCP Client，通过 StreamableHTTP 去调用天气 MCP Server。

#### 票务Agent（A2AServer）

专门处理车票、票务查询；内部自带LLM、MCP Client。

#### 旅行服务Agent（A2AServer）

处理旅行相关服务，例如订票、景点服务；内部自带LLM、MCP Client。

> **补充**：下面的MCP Server 不属于 Agent，是工具服务，负责执行工具逻辑，不属于智能体。

---

### 二、完整项目工作流

**示例用户问题：帮我查询明天成都天气，然后预定明天上午广州到成都的高铁**

#### 第一步：用户输入query，请求交给【路由Agent】

路由Agent 内部 LLM+Planning&React 模块理解用户需求，做任务拆解，通过AgentNetwork 发现可用的子 Agent，把任务分发给对应的子 Agent：

- 天气任务 → 天气Agent
- 订票票务任务 → 票务 Agent / 旅行服务 Agent

Agent 之间通信使用 **A2A 协议**。

#### 第二步：各个子Agent 执行子任务

天气Agent、票务 Agent、旅行服务 Agent 收到分配过来的任务；子 Agent 内部的 MCP Client 通过 StreamableHTTP 通信方式，调用对应 MCP Server。

- 天气Agent → 天气 MCP Server（工具：query_weather）
- 票务Agent → 票务 MCP Server（工具：query_ticket）
- 旅行服务Agent → 旅行服务 MCP Server（工具：order_ticket）

#### 第三步：MCP Server 执行工具逻辑，访问数据层拿真实数据

MCP Server 调用底层能力：

- 天气MCP Server 调用第三方和风天气 API 获取天气数据；
- 票务、旅行服务MCP Server 读取 MySQL 数据库；
- 旅行服务同时使用Milvus 向量库，做轻量 RAG 检索。

#### 第四步：结果逐层回传

数据层结果返回MCP Server → 返回 MCP Client 给到子 Agent；各个子 Agent 处理完任务，把结果通过 A2A 协议回传给顶层路由 Agent。

#### 第五步：汇总输出

路由Agent 汇总全部子任务结果，交给LLM 整合，输出完整旅行规划，返回给用户。

---

### 三、如果路由Agent 自己挂了怎么办？

Agent之间任务断了，就靠A2A识别任务出错，先试着重新跑几次；实在跑不通就把能拿到的结果返回给用户，重要任务就询问用户怎么处理，同时做好记录隔离，防止一个任务崩掉连累整个系统。

---

### 四、路由agent如何下发任务给其他子agent？

路由Agent 先通过 LLM 做任务拆解，再去 **AgentNetwork 智能体网络**，查看各个子Agent 的 AgentCard 名片，找到匹配能力的子 Agent；然后通过 A2A 协议，把封装好的 Task 任务发送给目标 A2AServer 子 Agent。

## 再次重申

### 完整链路流程

用户向Client Agent提交任务，任务经Server Agent、MCP客户端、MCP服务端下发至Tool执行，执行结果再沿原链路逐层回传，最终由Client Agent向用户输出结果。

### 评估指标

项目整体从 **三大维度** 量化系统效果：

1. **工具调用 召回率**：校验智能体能否精准识别用户需求、匹配对应天气/票务/路线等工具，提升需求匹配完整度，减少工具漏调用；
2. **端到端 时延**：统计从用户发起对话输入，到多智能体协同调用MCP服务、整合生成完整出行方案的整体耗时，优化并发场景下响应速度；
3. **工具 输入输出准确率**：规范MCP工具统一入参、返回值格式，校验智能体传给工具的请求参数、工具回传结果解析的正确性，降低参数错误、数据解析异常问题，提升系统整体容错与稳定度。
