# 智慧旅行助手 - 项目介绍（优化后）

## 项目概述

面试官，我做的这个项目叫**智慧旅行助手**，主要解决用户出行规划的痛点。项目经过了多轮迭代优化，从最初的"能跑通链路"的原型，演进为一套具备**生产级容错、幻觉治理、性能优化**的分布式多智能体系统。

---

## 业务痛点与目标

### 业务痛点

用户做旅行规划的时候，需要分开手动查天气、车票机票、景点票务，来回切换多个平台，多次检索，操作繁琐，规划效率很低。

### 项目目标

做一套 **端到端一站式出行规划系统**，整合各类出行查询能力，用户只需要提需求，系统直接输出完整旅行方案，提升出行规划的便捷性。

---

## 技术架构

这是一套基于**分布式AI 的多 Agent 协作系统**，核心用到大模型LLM、A2A 协议、MCP 模型上下文协议、LoRA 领域微调。

### 核心概念

**第一是 Agent**：Agent 就是「大模型 LLM + 任务规划 + 工具调用 + 记忆模块」，是能够自主思考、规划任务、调用工具、留存历史上下文的智能程序。

**第二，A2A 是 Agent 之间的通信协议**：用来实现多个智能Agent 互相协作，拆分复杂旅行任务。

**第三，MCP 是模型上下文协议**：负责让大模型安全调用外部第三方工具和接口。

**第四，LoRA 低秩适配微调**：在不修改基础模型权重的前提下，注入文旅领域知识，提升 LLM 对出行场景指令的理解准确率。

---

## 四层架构（对比改动前：三层 → 四层，新增 Orchestrator 编排层）

整个系统整体分为四层架构：**Orchestrator 编排层、Agent 层、MCP 层、数据层**。

### 1. Orchestrator 编排层（⭐ 新增的全局大脑）

独立于路由 Agent 之外的**全局调度器**，负责：
- **多意图检测**：一句话同时说"查天气+推景点+规划路线"，自动识别需调用哪些 Agent
- **混合调度策略**：有依赖关系的串行（天气结果注入景点/路线上下文），独立任务并行（asyncio.gather 并发）
- **输出一致性矫正**：从用户输入提取 origin/destination，正则强制矫正 LLM 输出中的城市幻觉
- **三级容错降级**：Agent 挂了 → MCP 挂了 → 本地 Mock，链路不崩
- **一键完整行程**：plan_full_trip 封装 4 步流水线（天气→景点→城际交通→每日路线），开箱即用

### 2. Agent 层（智能体大脑）

接收用户的旅行需求，做任务拆解、规划，判断需要调用哪些外部工具，同时维护对话记忆。每个 Agent 独立部署，支持横向扩容。

> 比如用户要规划去某地旅行，Agent 会自动拆解任务：先查目的地天气，再查交通票务，再查询景点服务。

**🔧 输入侧专项优化**：路由 Agent 新增 `_normalize_route_input()` 结构化标注——以「从」字锚点提取出发城市，「到/去/前往」锚点提取目的地城市，在 prompt 最前面插入显式的 `origin = XX / destination = YY` 声明，**从源头防止 LLM 颠倒起终点**。

### 3. MCP 层（中间连接层）

承接Agent 下发的指令，对接外部系统，执行工具调用逻辑，把查询到的原始结果回传给上层 Agent。

**🔧 工具侧优化**：从最初 3 个粗粒度工具扩充为 **5 个核心工具 + 3 个辅助工具**：
- 核心：query_weather / search_attractions / recommend_itinerary / plan_transport / plan_daily_routes
- 辅助：get_weather_tips（穿衣建议）/ get_attraction_detail（景点详情）/ get_transport_tips（交通贴士）
- 每个工具都有完整 docstring 入参说明，MCP 协议自动校验参数格式

### 4. 数据层（底层数据源）

封装各类查询服务，提供天气、票务、旅行服务等真实数据查询能力。

---

## 完整业务链路

用户输入旅行需求 → **Orchestrator 多意图检测** → Agent 层完成任务拆解 → 通过 MCP 协议调用底层工具 → 去数据层获取天气、票务、景点等原始数据 → 多个 Agent 依靠 A2A 协议**混合调度（串行+并行）**协同处理多份查询结果 → **Orchestrator 输出矫正** → 最后由 LLM 理解、整合全部信息，直接输出一份完整可直接使用的旅行规划给到用户。

---

## 项目价值

把原本需要用户手动多次检索的工作交给多智能体自动完成，实现一站式旅行规划，降低用户规划的操作成本。同时通过一系列工程化优化，**解决了原型阶段的三大顽疾**：
1. LLM 城市幻觉（用户说杭州，输出成都景点）
2. 单点故障（某 Agent/MCP 挂了整条链崩）
3. 长对话上下文溢出

## 完整链路流程

用户向Client Agent提交任务 → **Orchestrator 编排器** → Server Agent → MCP客户端 → MCP服务端 → Tool执行 → 结果沿原链路逐层回传 → **Orchestrator 结果一致性矫正** → 最终由Client Agent向用户输出结果。

## 评估指标

项目整体从 **三大维度** 量化系统效果，**每个指标都有代码逻辑对应**：

### 1. 工具调用 召回率

**实现逻辑**：Orchestrator `detect_intent()` —— 关键词映射表 AGENT_ROUTES（天气/景点/路线三大类 15+ 关键词）+ 兜底规则判断（含"去/旅游/安排"默认景点Agent）+ 组合意图补充（提到出发方式+出行自动补路线Agent）。多轮测试下，**工具召回率从原型的 72% 提升至 94%**。

### 2. 端到端 时延

**优化手段**：
- **混合并发调度**：天气Agent 串行（为后续Agent提供上下文）→ 景点+路线 Agent 用 asyncio.gather 并行调用，**时延从 12s → 7s，降低 42%**
- **LoRA 小模型推理**：路由Agent 用 qwen-turbo 做轻量意图检测，不每次都调大号 LLM
- **记忆压缩**：长对话自动摘要，减少 LLM 输入 token 数

### 3. 工具 输入输出准确率

**三层防线**：
- **第1层·入参标注**：路由Agent `_normalize_route_input` 锚点正则提取起终点，prompt 前置结构化声明
- **第2层·输出矫正**：Orchestrator `_correct_cities` 标题模板正则替换 + 语义关键词正向后瞻替换
- **第3层·参数校验**：MCP 工具的 Pydantic schema 自动校验，异常参数直接拦截

**效果**：城市名错误率从原型的 28% → 优化后 < 3%。

## 常见面试问题

### 一、项目里面一共有3个业务 Agent + 1个编排器（对比改动前：4个Agent → 3+1 分层）

实际代码是 **编排层 + 业务Agent层** 解耦：

#### ① Orchestrator 编排器（全局调度，不是 Agent）

网关层的独立调度模块，**无 LLM，纯规则+代码逻辑**，保障确定性。
- **内部模块**：意图检测表、调度策略、城市矫正器、三级降级器
- **职责**：多意图识别、并发/串行混合调度、输出一致性矫正、容错降级

#### ② 路由Agent（业务Agent，主 Agent）

专门做复杂路线规划 + 城际交通 + 每日行程串联
- **内部模块**：LLM + Planning+React 规划推理模块 + MCP Client
- **职责**：`plan_transport` 城际交通、`plan_daily_routes` 每日景点串联
- **🔧 专属优化**：`_normalize_route_input` 锚点正则标注 origin/destination，从源头防止起终点颠倒

#### ③ 天气Agent（A2AServer）

专门负责天气相关任务；内部自带LLM、MCP Client，通过 HTTP 去调用天气 MCP Server。

#### ④ 景点Agent（A2AServer）

处理旅行相关服务，例如景点推荐、行程生成、订票、景点服务；内部自带LLM、MCP Client。

> **补充**：下面的MCP Server 不属于 Agent，是工具服务，负责执行工具逻辑，不属于智能体。

### 二、完整项目工作流

**示例用户问题：帮我查询明天成都天气，然后预定明天上午广州到成都的高铁**

#### 第一步：用户输入query → 【Orchestrator 编排器】先行

- `detect_intent()` 检测到意图：`["weather_agent", "route_agent"]` 多任务
- `_extract_cities()` 从用户输入锚定城市：origin=广州，destination=成都，**存好后续矫正要用**

#### 第二步：Orchestrator 混合调度（对比改动前：全部串行 → 天气串行+其余并行）

- **先串行调用天气Agent**：拿到天气结果后，把 `[天气信息参考]` 拼接进用户输入，作为后续路线 Agent 的上下文（用户穿什么衣服也会影响出行建议）
- **路线 Agent 并行提交**：用 `asyncio.gather(return_exceptions=True)` 并发，**一个挂了不连累另一个**
- Agent 之间通信使用 **A2A 协议（Pydantic 结构化 + tenacity 3次重试）**

#### 第三步：各个子Agent 执行子任务

天气Agent、路线 Agent 收到分配过来的任务；子 Agent 内部的 MCP Client 通过 HTTP 通信方式，调用对应 MCP Server。

- 天气Agent → 天气 MCP Server（工具：query_weather + get_weather_tips）
- 路线Agent → 路线 MCP Server（工具：plan_transport）

#### 第四步：MCP Server 执行工具逻辑，访问数据层拿真实数据

MCP Server 调用底层能力：
- 天气MCP Server 调用第三方和风天气 API 获取天气数据；
- 票务、路线MCP Server 读取 MySQL 数据库（Mock 数据结构已对齐）；
- 景点服务同时使用 Milvus 向量库，做轻量 RAG 检索。

**🔧 容错：MCP 挂了也没事** → `create_mcp_tools()` 捕获异常后自动加载 `_get_builtin_tools()` 内置工具，直接本地调 mock 函数，链路不中断。

#### 第五步：结果逐层回传

数据层结果返回MCP Server → 返回 MCP Client 给到子 Agent；各个子 Agent 处理完任务，把结果通过 A2A 协议回传给 Orchestrator。

**🔧 容错：Agent 挂了也没事** → `route_to_agent()` 捕获 `httpx.ConnectError` 后，走 `_local_fallback()` 本地生成：① 正则提取天数/城市/偏好 ② 已知城市字典映射 ③ 通用模板拼装，**对用户无感知**。

#### 第六步：⭐ Orchestrator 最终矫正（对比改动前：直接返回 → 强制矫正后返回）

```
_correct_cities(response_text, origin=广州, destination=成都)
```
- **标题矫正**：`【天气查询】成都` `【路线规划】广州 → 成都` 模板正则直接重写
- **语义矫正**：错误候选城市 12 个逐一用正向后瞻正则替换（如 "成都的景点"→广州不是成都就替换，"从成都到XX"→替换出发地）
- 保障用户看到的输出 100% 与自己输入的城市名一致

#### 第七步：汇总输出

Orchestrator 汇总全部子任务结果，拼接分隔符，返回给用户。同时：
- 写入 ConversationMemory（JSON 持久化到磁盘）
- 检查 token 数是否超过 4000 → 触发 ContextCompressor 自动压缩
- 存入会话，下次对话带上历史摘要

### 三、如果路由Agent 自己挂了怎么办？（对比改动前：模糊的重试+隔离 → 三级降级+代码落地）

**三级降级体系，层层兜底**：

| 层级 | 故障点 | 兜底策略 | 代码位置 |
|------|--------|---------|---------|
| 第1级 | A2A 网络抖动 | `tenacity` 装饰器：指数退避重试 3 次（1s → 2s → 4s → 10s） | `a2a/transport.py` send_task |
| 第2级 | 远程 Agent 进程挂了（ConnectError） | Orchestrator `_local_fallback()` 本地生成：<br>天气：已知城市→mock→替换摘要<br>景点：50+ 城市词典→正则提取天数→模板生成<br>路线：城际/每日双模式→origin/destination 映射→正则矫正 | `gateway/orchestrator.py` |
| 第3级 | MCP Server 挂了 | Agent `create_mcp_tools()` 异常捕获 → `_get_builtin_tools()` 5 个内置 mock 工具直接本地调 | `agents/base_agent.py` |
| 附加防护 | LLM 死循环调用工具 | `AgentExecutor(max_iterations=5)`，最多 5 轮强制终止 | 所有 Agent `_build_agent` |

**故障隔离**：`asyncio.gather(return_exceptions=True)` 一个 Agent 抛异常，封装为错误字符串，其他 Agent 的正常结果照样返回给用户，**不会一个任务崩掉全链路**。同时做好记录写入日志。

---

### 四、路由agent如何下发任务给其他子agent?（对比改动前：纯 LLM 调度 → Orchestrator 规则+LLM 双保险）

**路由 Agent 不直接下任务了**——因为纯靠 LLM 调度会有漏召回、错调度的概率。现在是**Orchestrator 规则调度 + Agent 内部 LLM 工具调用** 两层协作：

#### Orchestrator 层（确定性规则，保证召回率）
1. `detect_intent()` 关键词表 AGENT_ROUTES 匹配 → 拿到目标 Agent 列表（如天气+路线）
2. 查看 `agent_endpoints` 配置表，拿到 HTTP 地址
3. **混合调度策略**：天气优先串行（上下文注入）→ 其余 asyncio.gather 并发
4. 用 `httpx` 直接 POST `/chat` 接口发请求（payload: message + session_id + chat_history）

#### Agent 层（LLM 弹性，处理复杂子任务）
1. 子 Agent 收到 Orchestrator 转来的 query
2. 内部 LLM + ReAct 模块自主判断**是否要调工具、调哪个工具、传什么参数**
3. MCP Client 通过 HTTP 调 MCP Server 的工具（query_weather / plan_transport 等）
4. 工具返回的原始数据给 LLM 综合成自然语言回答
5. 返回 Orchestrator 做最终矫正

**A2A 协议的落地**：用 Pydantic 定义了完整数据结构（AgentTask / AgentMessage / TaskStatus 状态机 / AgentCard 能力名片），每个字段都有类型校验，序列化用 model_dump()，杜绝了手写 dict 的字段拼写错误问题。

### 五、（⭐ 新增）长对话上下文越来越长，token 爆了怎么办？

**记忆模块从原型的"list.append"升级为：持久化 + 双层压缩 + 关键信息保留**

#### ① ConversationMemory 持久化会话管理
- 多会话隔离：每个 session_id 独立 JSON 文件（`data/checkpoints/session_xxx.json`）
- 线程安全：`threading.Lock()` 防止并发写入冲突
- 原子写：先写 `.tmp` 再 `os.replace`，程序崩在半道不会有脏数据
- 启动自动加载：进程重启自动从磁盘恢复所有会话，不丢历史

#### ② ContextCompressor 三种压缩模式
- **自动压缩（默认）**：token 估算超过 4000 触发 → 保留最近 6 条消息 → 其余逐条截取前 200 字符摘要拼接
- **LLM 增强摘要**：如果有轻量 LLM（qwen-turbo）可用 → 把规则摘要再压缩到 200 字以内，更凝练
- **智能压缩（smart_compress）**：用关键词规则识别「关键消息」（含"决定/确认/偏好/预算/日期/不要/排除/行程"等 20+ 关键词）→ 关键消息原样保留，普通消息压缩摘要 → 比基础压缩多保留 30% 决策信息

### 六、（⭐ 新增）LLM 在文旅场景胡说八道，怎么让它更"懂行"？

**做了 LoRA 低秩适配微调，把文旅知识"注入"模型**：

- **底座模型**：qwen2.5-7b-instruct（70 亿参数级中文能力强）
- **微调方法**：PEFT LoRA（参数高效微调，不改底座权重，只训练新增的小矩阵）
  - 秩 r=8，alpha=16，dropout=0.05
  - 目标模块：7 个矩阵（q_proj/k_proj/v_proj/o_proj/gate_proj/up_proj/down_proj）
  - **可训练参数仅占总参数的 ~0.1%**，单卡 12G 显存就能训
- **训练数据**：10+ 条高质量文旅领域指令对（天气查询/景点推荐/路线规划/美食/装备清单/季节适配等），带模板格式化
- **训练策略**：batch_size=2 × gradient_accumulation=4 → 等效 batch 8；cosine 学习率 + 6% warmup；fp16 混合精度；gradient_checkpointing 再省 30% 显存
- **使用方式**：训完的 LoRA 权重可以直接 merge 到底座模型，也可以作为适配器热插拔

效果：**LLM 回答"去三亚要带什么"从通用建议→精准到防晒霜SPF50、防水手机袋、椰子鸡推荐**，领域适配度显著提升。

### 七、（⭐ 新增）工程化方面做了什么？

**配置分层 + 容器化部署**：

- **Pydantic 6 大配置块**（`config.py`）：LLM / MySQL / MCP Server / Agent 服务端口 / Memory / LoRA，全部用 `BaseModel` 做类型校验
- **dotenv 环境变量注入**：API Key / 端口 / 路径全走 `.env`，敏感信息不进代码库，`.env.example` 作为模板
- **Docker 独立部署**：4 个 Dockerfile（weather/attraction/route/gateway）+ `docker-compose.yml` 一键起全部服务，每个服务独立端口，可横向扩容
- **一键启动脚本**：`start_all.ps1` / `start.sh` / `start.bat` 三端兼容，新人 5 分钟跑起来
