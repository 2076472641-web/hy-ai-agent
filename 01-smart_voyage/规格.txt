这个项目我只需要记住：

**1个业务问题 + 4个技术痛点 + 6类指标 + 4类工程数字 + 3类业务价值。**

---

## 1个业务问题

旅游信息和服务比较分散。

用户需要分别查询：

天气、路线、票务、景点等信息。

所以我们希望通过一个统一的 AI 入口，让用户通过自然语言提出需求，系统自动完成任务拆解、Agent 协作、工具调用和结果整合。

---

## 4个技术痛点

### ① 业务复杂 → Multi-Agent

天气、路线、票务、景点业务职责不同。

单 Agent 如果挂载大量 Tool，Prompt、工具选择以及业务逻辑都会越来越复杂。

所以拆分成多个专业 Agent。

---

### ② 实时数据 → MCP

天气、票务等信息是实时变化的，不能只依赖 LLM。

所以需要调用外部 Tool。

Tool 越来越多以后，如果 Agent 直接和 API 强耦合，不方便维护和扩展。

所以通过 MCP 对工具服务进行标准化封装。

---

### ③ 多 Agent 协作 → A2A

Agent 拆开以后，需要解决不同 Agent 之间任务传递以及结果协同的问题。

所以通过 A2A 完成 Agent 之间的任务交互。

---

### ④ 多轮对话 → Redis + 上下文压缩 + MySQL

旅游规划往往是多轮的。

需要保留上下文。

但是完整历史不断进入 LLM，会造成 Token 增长和推理延迟增加。

所以：

Redis 保存高频会话上下文；

长对话进行压缩；

MySQL 保存完整会话记录。

# 二、2～3分钟完整项目介绍

面试官您好，这个项目是一个面向文旅出行场景的多智能体系统。

项目主要解决的是旅游过程中信息和服务比较分散的问题。

比如一个用户准备去北京旅游，他可能需要分别查询天气、路线、景点以及票务信息，需要在多个平台之间不断切换。

所以我们的目标是通过一个统一的 AI 对话入口，让用户只需要描述自己的出行需求，系统就能够自动理解需求，并调用不同的业务能力，最终生成一套完整的旅行方案。

整个系统在设计过程中，我主要把它理解成四个核心问题。

第一个问题是业务比较复杂。

天气、路线、票务、景点推荐本身属于不同的业务领域，如果全部放在一个 Agent 里面，随着 Tool 和 Prompt 越来越多，Agent 的职责会越来越重。

因此我们采用 Multi-Agent 架构，将系统拆分成意图识别 Agent、天气 Agent、路线 Agent、票务 Agent、景点推荐 Agent 等，让不同 Agent 专注处理自己的业务任务。

第二个问题是实时数据。

像天气和票务这样的数据不能完全依赖 LLM 本身，所以 Agent 必须能够调用真实业务工具。

但是随着工具越来越多，如果每个 Agent 都直接适配不同 API，Agent 和业务接口之间的耦合会比较严重。

因此我们通过 MCP 对天气查询、票务查询等能力进行标准化封装，让上层 Agent 更多关注“调用什么工具”，而不需要过度关心底层 API 是怎么实现的。

第三个问题是 Multi-Agent 拆分之后的协作。

不同 Agent 之间需要完成任务传递和结果返回，所以项目里面通过 A2A 的方式实现不同 Agent 之间的任务协作。

比如用户说：

“帮我规划北京三日游，同时看看天气并推荐一些景点。”

系统首先理解用户 Query，然后拆分成天气查询、景点推荐和行程规划等任务。

不同任务会交给相应 Agent。

如果天气 Agent 需要获取实时数据，就通过 MCP Client 请求 MCP Server，再由 MCP Server 调用具体的天气 Tool。

数据获取完成以后逐层返回给 Agent，最后由上层 Agent 汇总多个 Agent 的结果，通过 LLM 生成最终旅行方案。

第四个问题是多轮对话。

旅游规划通常不是一次问答就结束，所以我们需要保留用户上下文。

项目里面通过 Redis 保存高频会话上下文，对比较长的历史会话进行压缩，减少重复 Token 和推理开销，同时使用 MySQL 对完整会话记录进行持久化。

最后在工程部署方面，我们将不同 Agent 和相关服务通过 Docker 拆分部署，使各个业务服务能够独立扩展和维护。

最终这个项目不仅完成了一个 AI 问答系统，而是把：

**用户需求理解 → Agent 调度 → Agent 协作 → MCP Tool 调用 → 真实业务数据 → LLM 生成 → 用户结果**

串成了一条完整的 AI 业务链路。

# 十六、如果面试官问：怎么降低成本？

我会从几个层面处理。

第一，减少无意义的大模型调用。

可以通过规则、路由或者小模型处理简单任务。

第二，控制上下文长度。

通过摘要压缩和状态抽取降低输入 Token。

第三，缓存重复查询。

例如天气、景点等短时间内重复 Query 可以使用缓存。

第四，Agent任务并行化。

对于没有依赖关系的天气查询和景点查询，可以考虑并行执行，减少整体等待时间。

第五，模型分层。

简单任务使用小模型，复杂任务再交给大模型。

所以成本优化的核心并不是简单换一个便宜模型，而是：

**减少不必要的模型计算。**

这样可以在效果、延迟和成本之间取得更好的平衡。

# 二十三、最后只背这12句话

如果时间已经非常非常紧，我只背下面这些。

**1. 旅游业务复杂，所以采用Multi-Agent进行职责拆分。**

**2. 实时天气和票务不能依赖LLM，所以需要外部Tool。**

**3. Tool越来越多，所以通过MCP进行标准化和解耦。**

**4. Agent拆分以后需要协作，所以通过A2A完成任务交互。**

**5. 多轮对话需要Memory，所以使用Redis保存高频上下文。**

**6. 历史越来越长，所以进行上下文压缩，MySQL保存完整记录。**

**7. 效果主要看Task Success、Routing Accuracy和Tool Success。**

**8. 性能主要看平均延迟、P95/P99以及各节点耗时。**

**9. 成本主要看GPU、Token、第三方API以及每次成功任务的成本。**

**10. 业务价值主要体现在减少用户操作、减少重复人工咨询以及SaaS复用。**

**11. Multi-Agent不是越多越好，简单任务我更倾向于单Agent或者Workflow。**

**12. 这个项目最大的价值，是把LLM、Agent、A2A、MCP、Tool和真实业务数据串成了一条完整的AI应用链路。**
